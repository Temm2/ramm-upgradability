Contract Upgradability

Onboarding brief and task list — prepared for the engineer picking up upgradability as their primary workstream. Read the current-state section before touching anything; it explains exactly what "upgrade" means in this codebase today (redeploy everything, by hand) and why that stops working before mainnet.

Owner: you Prepared: August 2026 Repo: contracts/ + agents/src/valet/
01

Current state

Nothing in this codebase is upgradeable in the real sense — a logic swap that preserves existing storage at a stable address. Checked directly: every contract imports plain @openzeppelin/contracts, never the -upgradeable variant. There is no Initializable, no UUPSUpgradeable, no proxy of any kind anywhere in contracts/src/.

One piece of indirection exists — RammRegistry.sol — and it's worth understanding precisely, because it's easy to mistake for more than it is. It's a plain Ownable contract holding four addresses (rammToken, redemptionNFT, vestingVault, promoStaking), each swappable via an onlyOwner setter. Every IMPXMarket stores only the registry's own address as immutable and resolves the four singletons fresh on every call — so swapping which contract is authoritative no longer means redeploying all 54 markets. That's real, and it's already shipped.

What it doesn't do: preserve state. Pointing the registry at a new VestingVault gives every market a contract with zero balance and zero tranches — it's changing a signpost to point at a new building, not renovating the one that's standing. That's fine for a fix that doesn't need the old instance's data. It's useless the moment real value is sitting in the contract you need to fix — which, on mainnet, is the normal case, not the exception.

The actual constraint

Every contract in this table is owned by a single EOA (DEPLOYER_PRIVATE_KEY) — the same key that would hold upgrade authority under any scheme you design. One compromised or lost key currently controls every admin function in the system. Whatever you build, this is part of the problem, not a footnote to fix later.

02

Why now, not later

Two real operations this month prove the cost, not a hypothetical.

2026-08-24

RammRegistry migration

Shipped the registry indirection layer above. Required redeploying all 54 markets from scratch to adopt the new constructor shape. Missed step, found later: the demo wallet's displayed holdings orphaned against the old addresses — had to be manually repopulated.

54 redeploys · 1 missed migration step
2026-08-26

Bonding curve parameterization

Fixed the curve's inflection point being fixed at supply 500 regardless of a market's real supply cap. Required redeploying all 54 markets again. Missed step, found the hard way: the redemption-code vault was still keyed to the previous migration's addresses — every real redemption returned a blank code until it was reseeded.

54 redeploys · 1 missed migration step

Same root cause both times: redeploying a contract orphans everything keyed to its old address — not just other contracts, but off-chain stores too (a JSON vault, a wallet's displayed balance, an indexer's watch list). Each fix needed its own audit script written after the fact to prove nothing was missed. On testnet, an orphaned demo wallet is a minor annoyance. On mainnet, it's real users' holdings abandoned on a contract nobody's fixing anymore — not an option, not a "migrate later." This has to be solved before the first mainnet deploy, not after the first mainnet bug.

03

The task list

Roughly sequential — later tasks assume earlier ones are settled, but read all seven before starting task 1 so early decisions account for what's coming.

1

Map the real blast radius

Before designing anything, confirm the inventory above against the actual deployed state — don't take this document's word for it.

Run agents/src/scripts/auditRegistry.ts, auditOwnership.ts, and auditVaultAuthorization.ts against the live 54 markets. Read RammRegistry.sol and both migration commits (git log --oneline --all | grep -i registry, git log --oneline --all | grep -i curve) end to end — they're the reference implementation for what a "migration" currently means here, scripts and all.

Done when

  • You can list, from memory, every off-chain store that got orphaned by the two incidents above and why.
  • You can explain why RammRegistry solves address discovery but not state preservation, to someone who hasn't read this doc.
2

Choose and justify a proxy pattern for the four singletons

RAMMToken, RedemptionNFT, VestingVault, PromoStaking — one instance each, real state, the easier half of this problem.

Evaluate UUPS (UUPSUpgradeable, upgrade logic lives in the implementation, cheaper per-deploy) against the Transparent Proxy pattern (upgrade logic lives in a separate ProxyAdmin, slightly more gas per call). Recommend one in writing with the tradeoff stated, not just the choice. Convert these four contracts to their @openzeppelin/contracts-upgradeable equivalents behind ERC1967Proxy. RammRegistry then points at proxy addresses that never change again — its own job shrinks to pure discovery.

Done when

  • A written recommendation (UUPS vs. Transparent) with the reasoning, reviewed before any code lands.
  • All four contracts deployed behind proxies on a testnet fork, with a forge test proving an upgrade preserves existing balances/tranches/stakes.
3

Design the per-market upgrade path

54 instances of IMPXMarket + PVTToken, not one — the actual hard part, and the one with no precedent yet in this codebase.

Evaluate three shapes: (a) EIP-1167 minimal clones per market pointing at one shared UUPS-upgradeable implementation — one upgrade transaction fixes all 54 at once; (b) full ERC1967Proxy per market — more gas per deploy, same one-upgrade-fixes-all property; (c) push bonding-curve and fee-split logic into a shared upgradeable "MarketLogic" singleton that thin markets call into, leaving markets themselves non-upgradeable but shrinking what a future bug can actually live in. Recommend one — (a) is the standard answer for many-instances-of-similar-contract and should be the default unless there's a concrete reason against it here.

Done when

  • A written design doc covering the chosen shape, VALET's createCampaign() changes needed to deploy clones instead of full contracts, and how a single upgrade transaction is proposed/verified/executed.
  • A forge test deploying 3+ market clones, upgrading the shared implementation once, and confirming all 3 reflect the fix with zero per-market redeploys.
4

Storage-layout discipline

The single most common way upgradeable contracts silently corrupt themselves — this needs to be a hard rule the team can't accidentally break, not a thing to remember.

Document (and where possible, enforce via CI) the OpenZeppelin storage-gap convention: new state variables only ever appended, never inserted or reordered; reserved uint256[50] private __gap slots on every upgradeable base. Check whether OpenZeppelin's Foundry Upgrades plugin fits this project's existing Foundry setup — it validates storage layout compatibility automatically on every proposed upgrade.

Done when

  • A written rule in the contracts README, plus a CI check (or documented manual step if CI integration isn't feasible yet) that fails a PR introducing a storage-incompatible change.
5

Move upgrade authority off a bare EOA

One private key currently controls every admin function in the system — the callout in section 1 isn't a side note, it's the other half of this task.

Propose a Gnosis Safe multisig (minimum viable) or a TimelockController in front of it (better — gives users a window to react to a proposed upgrade before it executes) as the owner of every upgradeable proxy's admin functions and RammRegistry's onlyOwner setters. Write the runbook: who proposes an upgrade, who signs, how long the delay is, how it's communicated before it executes.

Done when

  • A Safe (or timelock) deployed on testnet actually holding ownership of the upgraded contracts from tasks 2-3, with a real test upgrade proposed and executed through it end to end.
  • A short runbook doc a non-engineer (e.g. whoever handles the mainnet audit) can review and understand.
6

The one last full migration

The 54 live markets predate all of this — they need to move onto the new architecture exactly once, then never again for a logic fix.

Reuse the proven script sequence from the two migrations documented in section 2 (deployDemoProducts.ts → migrateCampaignContracts.ts → liquidity reseed → vault-code reseed → the three audit scripts → affected wallet repopulation) as the reference implementation — extend it to deploy clones/proxies per task 3 instead of plain contracts, don't rewrite the off-chain migration logic from scratch. This is deliberately the last task, not the first: doing it before tasks 2-3 land means doing it twice.

Done when

  • All 54 markets running on the upgradeable architecture, verified by the same three audit scripts plus a new one confirming every market resolves to the correct shared implementation.
  • A real on-chain buy, sell, and redeem against a migrated market, confirmed by hand — same bar the previous two migrations were held to.
7

Write the upgrade runbook

So the next person who needs to ship a contract fix doesn't have to re-derive any of this from git history.

One doc, checked into contracts/: the chosen patterns and why, the storage-layout rule, who holds upgrade authority and how a proposal moves through them, and a step-by-step "how to ship a logic fix" walkthrough that ends in one upgrade transaction — not a 54-market redeploy.

Done when

  • A teammate who wasn't involved in tasks 1-6 can follow the runbook alone to ship a trivial test fix on testnet.
