RammRegistry.sol now sits between every market and the four shared singletons (RAMMToken/RedemptionNFT/VestingVault/ PromoStaking) — IMPXMarket stores only the registry's address as immutable and resolves the rest fresh on every call. Local devnet — a real, specific op-geth bug, not an environment issueIn progress

Superchain contracts genuinely deployed onto a live Base Sepolia fork via op-deployer; op-node independently recognizes the config as l1_network: base. Ruled out, one by one, with direct evidence rather than guessing:

  • Ruled out P2P discovery noise, archive vs. full sync mode, a stale L1 anchor (Base Sepolia reorged since the first deploy — redeployed fresh), container networking (a raw JWT-signed call straight to op-geth's own engine_getPayloadV3, bypassing op-node, still times out with zero response).
  • Ruled out op-node's retry behavior interrupting the build — at debug verbosity, found op-geth logging "Payload building already interrupted" on every retry. Tested directly: stopped op-node entirely, gave op-geth 30+ uninterrupted seconds, called getPayload manually — still zero response. The interrupt logs were a real but secondary effect, not the cause.
  • Investigated the Jovian hardfork (activated at genesis, confirmed via op-deployer inspect deploy-config) as the likely underlying trigger — it's the newest, least battle-tested fork in this stack, and Base itself has separately flagged Jovian-adjacent op-geth issues. No override exists in this op-deployer version's "custom" intent type to genesis without it, and no readily available older release predates Jovian's Sepolia activation, so this couldn't be isolated further without building from source.

Net: a real, specific, well-evidenced op-geth bug building the very first payload on a Jovian-active custom genesis — not a config or environment problem on this end. Worth filing against ethereum-optimism/op-geth directly. Containers left running.

Bonding curve shape — parameterized, redeployed, liveFixed

Was a real gap, not just cosmetic: with a fixed inflection at supply 500 and real demo supply caps of 20-60, the curve never got anywhere near it — price barely moved (~$915-920) across a product's entire real supply range regardless of configured price. SigmoidMath.getPrice/getTotalCost now take a per-market CurveParams struct; deriveCurveParams() (agents/src/valet/curve.ts) turns a brand's actual (minPrice, maxPrice, totalSupply, fast/medium/slow) into it — verified to reproduce the original curve almost exactly at its own reference scale, stay monotonic across 200 randomized configs, and correctly span a demo-scale product's configured range instead of ~$5 of total movement. 63/63 contract tests passing. All 54 markets (41 demo + 13 campaigns) redeployed onto it — verified 54/54 wired to the registry, 0/54 wrong ownership, 0/54 unauthorized on VestingVault, liquidity funded, redemption vault codes reseeded from the start this time (the exact gap the "orphaned by the registry migration" item below describes — not repeated), and the demo wallet's holdings confirmed live in Folio against the fresh contracts.

SHOPi search — real semantic ranking built, waiting on a Voyage API keyIn progress

The client's local scorer (hand-tuned synonym/keyword matching against Claude Vision annotations) is unchanged and stays the fast first pass. The gateway's fallback search now does real cosine-similarity ranking over Voyage AI embeddings instead of a regex category/heel/flat pre-filter — the piece that actually broke as the catalog grew, since a brand-uploaded product in a category nobody hard-coded was previously invisible. Redemption codes orphaned by the registry migration — found and fixed this sessionFixed

Same shape of bug as the gasless-migration gap above, one layer down: redeploying the 41 demo products gave every one a fresh PVT address, but agents/data/vault.json's redemption codes were still keyed by the old ones. Every real redemption since the migration completed correctly on-chain but came back with a blank code — 0 of 41 products had codes under their current address. Reseeded (41/41 now seeded) and Folio now silently retries the vault for any redeemed-but-codeless PVT on screen focus, not just when the shopper manually taps "Get my code" — verified live against a real stuck record. Third time this exact "redeploy orphans anything keyed by the old address" shape has shown up this session (holdings display, on-chain authorization, now an off-chain data store) — worth a checklist pass over every address-keyed store before any future bulk redeploy.
